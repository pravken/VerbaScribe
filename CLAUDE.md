# Verbaliox — правила для сессий Claude

Локальная программа для Windows: запись и расшифровка встреч, анализ, перевод, дубляж. FastAPI + окно
pywebview (WebView2), SQLite, модели на ПК пользователя. Отвечай пользователю по-русски.

## Что нельзя без явной просьбы пользователя

- **Выпускать релиз** (тег `v*`, запуск Release с тегом). Сборка без тега — можно, она ничего не публикует.
- **Трогать ключ подписи.** `RELEASE_PUBLIC_KEY` в `app/updater.py` меняется только при смене ключа.
  Секрет `RELEASE_SIGNING_KEY` есть только в GitHub Actions и у автора офлайн: не создавай, не проси и
  не храни его (подробно — `docs/release-signing.md`).
- **Пушить в `main`.** Работа идёт в своей ветке, в `main` — через PR.

## Модели и пакеты

- Только бесплатные и разрешённые для коммерческого использования. Лицензия модели или пакета
  меняется в новой версии — остановись и спроси.
- Лицензии и атрибуция — в README (таблицы лицензий). Новый компонент добавляй туда же.

## Работа на ПК пользователя (локальная сессия)

- Не трогай настоящую папку данных (`%LOCALAPPDATA%\Verbaliox`; до первого запуска версии с новым именем — `%LOCALAPPDATA%\VerbaScribe`) и модели (`<папка программы>\models`):
  работай с копиями через `VERBALIOX_DATA_DIR` и `VERBALIOX_MODELS_DIR` во временных папках.

## Как вести изменения

- Одна тема — один коммит. Перед пушем: зелёные тесты, проверка в браузере для изменений интерфейса,
  просмотр своего диффа. Успех тестов проверяй по коду возврата, а не по выводу `tail`.
- В коммитах, PR и коде не пиши идентификаторы моделей Claude.
- GitHub — через MCP-инструменты (`gh` в облачной сессии нет).

## Проверки

```
python -m unittest discover -s tests -t .        # все тесты (в облаке: PYTHONPATH=tests/stubs)
python -m compileall -q app run.py build_exe.py tests
```

Браузерный smoke-тест — как в `.github/workflows/ci.yml`: сервер `uvicorn app.main:app --port 8799`
с временными `VERBALIOX_DATA_DIR`/`VERBALIOX_MODELS_DIR` (демо-записи: `python tests/ui/seed.py`), затем
`node tests/ui/smoke.mjs` и `node tests/ui/scenarios.mjs` (сценарии; `SHOTS=<папка>` — скриншоты шагов).

- **Стили:** `static/vendor/tailwind.css` собирается заранее. Новый класс Tailwind в разметке или
  скриптах — пересобери: `npm run vendor` (тест `test_every_class_has_its_css` это ловит).
- **Тексты:** каждая строка интерфейса — ключ в `static/i18n.js` (ru и en). Сообщения сервера на
  русском получают английский в `static/server_text.js` (тест проверяет).
- **Скрипты страницы:** без inline-обработчиков (CSP `script-src 'self'`): события через
  `data-click="fn"` и `data-click-args='[...]'` (диспетчер в `static/js/core.js`).

## Релиз (когда пользователь попросит)

Новое сначала выходит бетами (`vX.Y.Z-beta.N`, пре-релиз): их получают только те, у кого включено
«Настройки → Обновления → Получать бета-версии». Обычная версия `vX.Y.Z` — когда бета проверена.
Старые релизы и теги не удаляются.

1. Записать изменения в `CHANGELOG.md` (раздел `## X.Y.Z` по-русски и `## X.Y.Z — English`): он
   становится текстом страницы релиза (английский раздел там всегда первым, `tools/release_notes.py`), беты
   берут раздел своей будущей версии.
2. Поднять `__version__` в `app/__init__.py` (для беты — `X.Y.Z-beta.N`, тег должен совпадать),
   влить в `main` через PR.
3. Actions → Release → Run workflow на `main` с тегом `vX.Y.Z` (или `vX.Y.Z-beta.N`). Workflow сам
   собирает, подписывает `SHA256SUMS.txt`, проверяет подпись ключом из программы и публикует.
4. Релиз не собирают вручную и не загружают файлы руками: без подписи программа его не установит.

## Где что

- `app/` — сервер (`app/api/` — маршруты), `static/` — страница (`static/parts/` — части разметки,
  `static/js/` — скрипты одной глобальной области, `core.js` первым).
- `docs/audit-report.md` — аудит и что сделано, `docs/pc-session-audit.md` — что проверить на ПК,
  `bench-report/` — замеры моделей.
