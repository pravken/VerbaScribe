# Аудит VerbaScribe — отчёт

Ветка `claude/sweet-maxwell-uaextf`, коммит `ceb91b7`, версия 0.4.5. Дата: 2026-10-22.

**Как проводился.** Весь код прочитан построчно по пяти областям (HTTP-слой и безопасность; внешние процессы,
обновление, календарь, облако; серверная логика и данные; интерфейс; Windows-часть, сборка, зависимости,
лицензии). Каждая находка ниже прослежена от настоящего входа до последствия; то, что можно было, проверено
запуском: сервер в песочнице (Linux, без GPU), httpx-запросы ко всем 162 маршрутам, Playwright/Chromium
с тестовой базой (1002 записи, payload'ы во всех пользовательских строках), сконструированные zip-архивы
резервной копии и обновления, вредные .ics, замеры на базе 1,1 ГБ. Что проверить можно только на Windows,
отмечено как «подтверждено чтением». Код не менялся.

**Итог:** критично — 2, важно — 17, желательно — 46, идеи — 25. Главное:

1. Восстановление из резервной копии пишет файлы по любому пути с диска из `manifest.json` чужого архива
   (zip-slip) → выполнение кода при входе в Windows.
2. XSS через имя участника в списке «Люди» вкладки «Ассистент» → полный доступ к API из окна.
3. Правки реплик и участников теряются при параллельных запросах (read-modify-write всего транскрипта
   вне блокировки); побочные задания ставят `completed` отменённым записям, и ретенция затем удаляет их звук.
4. Архив обновления может писать за пределы папки программы; хеш проверяется только из того же релиза;
   автообновление перетирает git-клон; yt-dlp и окружение дубляжа ставятся без хешей.
5. Нет проверки `Origin` — страница с другого порта `127.0.0.1` ходит в API с cookie; настройки
   принимаются без проверки ключей и значений (адреса Ollama/облака → эксфильтрация расшифровок).
6. После восстановления копии пропадают ключи облачных моделей; один кривой `RRULE` ломает весь календарь;
   живые субтитры при отказе воркера растут в памяти и перезапускают процесс каждые 1,2 с.
7. Lock закрепил certifi/urllib3/requests 2022 года (с зеркала PyTorch); DOMPurify 3.1.6 с известным mXSS
   рендерит ответы LLM; ошибка импорта при старте — тихий отказ без журнала; при выходе FFmpeg захвата экрана
   остаётся сиротой; поиск окна по заголовку «VerbaScribe» ловит окно Проводника.

Оценка уверенности: **[З]** подтверждено запуском, **[Ч]** подтверждено чтением всего пути, **[П]** предположение.

## Критично

### К1. Восстановление резервной копии пишет файлы по произвольному абсолютному пути [З]
- **Где:** `app/backup.py:119-131` (`target = Path(str(f.get("path")))` — путь из манифеста архива;
  проверка `".."` применяется к имени записи `name` внутри zip, а не к `target`), вход `POST /api/backup/restore`
  (`app/api/library.py:151-163`).
- **Сценарий:** пользователю присылают «резервную копию VerbaScribe». В `manifest.json` элемент `media` с
  `path: C:\Users\<user>\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\x.bat`. Пользователь
  жмёт Настройки → Резервная копия → Восстановить. `target.parent.mkdir(parents=True)` создаёт папки, файл
  пишется (только если такого файла ещё нет). Проверено: сконструированный zip создал файл вне папки данных,
  `restore()` вернул `media_restored: 1`.
- **Последствия:** запись произвольного нового файла от имени пользователя → автозапуск скрипта при входе,
  подмена DLL рядом с программой. Плюс `meetings.db` из архива целиком заменяет рабочую базу при следующем старте
  (`apply_pending`), а в ней — настройки: `ollama_url`, `llm_base_url_openai_compat`, `llm_provider`,
  `llm_cloud_consent` → будущие расшифровки уходят на сервер автора архива (см. В6).
- **Исправление:** медиа восстанавливать только по относительному `name` внутрь известного корня
  (`UPLOADS_DIR`/папка записей): `p = (root / Path(name).name).resolve(); if root not in p.parents: skip`;
  поле `path` из манифеста использовать лишь как подсказку, куда это файл *был*. Перед записью показывать,
  сколько файлов и куда пишется. Настройки из восстановленной базы, задающие адреса и пути, сбрасывать или
  показывать пользователю на подтверждение.

### К2. XSS через имя участника в списке «Люди» (Ассистент) [З]
- **Где:** `static/js/library.js:440` — `onclick='setAskScope(${JSON.stringify({type:'person', name: p.name})})'`:
  JSON.stringify экранирует `"`, но не `'`, а атрибут в одинарных кавычках. Та же конструкция с id пресета:
  `static/js/studio.js:418` — `quickRecord('${p.id}')` без экранирования (`"` закрывает атрибут).
- **Сценарий:** имя участника попадает в базу без ограничений (вкладка «Участники» → `PATCH /speakers`, сервер
  обрезает до 120 символов, `app/api/library.py:563`; голосовой профиль `app/voice_profiles.py:150`; чужая
  резервная копия). Открытие вкладки «Ассистент» → `renderPeople()` → имя `Bob'><img src=x onerror=…>`
  выполняет JS. Проверено в Playwright: `window.__xss` установлен.
- **Последствия:** произвольный JS в окне с cookie сессии: чтение всех расшифровок, смена настроек (в т.ч.
  адресов LLM → утечка), удаление записей, `/api/open-url`, `/api/reveal`, установка обновления. Мост
  `window.pywebview.api` ограничен (`app_url`, `toggle_fullscreen`) — выполнения команд ОС напрямую нет.
  Сегодня вход требует действий самого пользователя или чужой копии, поэтому «критично» — по потенциалу:
  как только имя участника придёт из внешнего источника (календарь, LLM-подсказка), это станет
  дырой без участия пользователя.
- **Исправление:** данные никогда не вставлять в inline-обработчики: `data-name="${escapeHtml(p.name)}"` +
  `onclick="setAskScope({type:'person', name:this.dataset.name})"` (так уже сделано в `workspace.js:1063`);
  то же для `library.js:372/422` и `studio.js:418`. На сервере запретить `<>"'` в именах участников и
  валидировать `record_presets[].id` (`^[a-z0-9_-]+$`). Долгосрочно — CSP без `'unsafe-inline'` для скриптов
  (вынести inline-обработчики в `addEventListener`), тогда класс ошибок исчезнет.

## Важно

### В1. Правки реплик и участников теряются при параллельных запросах [З]
- **Где:** `app/api/analysis.py:149-181` (`api_update_segment`: `get_meeting` → изменение одного элемента →
  `save_meeting_results` всего `segments_json`), `app/api/library.py:555-591` (`api_update_speaker`),
  `app/database.py:1141-1171` (`merge_segment_with_previous`), `app/transcriber.py:151-158`
  (`clean_meeting_transcript`), `app/voice_profiles.py:174-188` (`apply_to_library`). `_db_lock` защищает
  только отдельные SQL-вызовы, не цикл «прочитал → изменил → записал».
- **Сценарий:** пользователь меняет участника у реплики A и сразу у B, пока первый PATCH (80–300 мс на
  транскрипте 2 МБ) ещё идёт; обработчики FastAPI выполняются параллельно в пуле потоков, второй перезаписывает
  результат первого. Проверено: 40 одновременных PATCH разных реплик → 23 потеряны; два переименования
  участников → одно потеряно.
- **Последствия:** правка молча пропадает; интерфейс после ответа показывает транскрипт без неё.
- **Исправление:** перенести read-modify-write в `app/database.py` под `_db_lock` одной транзакцией
  (`update_segment(meeting_id, segment_id, mutate)`, `update_speaker(...)`, merge), либо optimistic lock
  (колонка `segments_rev`, 409 при расхождении). Радикально — таблица `segments` вместо одного JSON (см. Идеи).

### В2. Побочные задания ставят `completed` отменённым/неудачным записям; ретенция затем удаляет их звук [З]
- **Где:** `app/transcriber.py:285-296` (`_run_side_job`: во всех ветках `status="completed"`), `:237-255`
  (`_run_dub_job`); `app/api/media.py:327-377` (`api_meeting_cut`) и `:379-445` (`api_video_subtitles`) не
  проверяют статус; `app/database.py:909-922` (`expired_media_ids` берёт `status='completed'`),
  `app/main.py:372-386` (`_retention_loop`).
- **Сценарий:** расшифровка отменена через 30 с — частичный транскрипт сохранён (`_PartialTranscript`),
  статус `cancelled` (или `failed`, `cleared`). Пользователь запускает «Запись без шума»/субтитры. По окончании
  (и при ошибке) запись становится `completed`, `progress=100`. Проверено: `cancelled` → `completed`.
- **Последствия:** обрывок выглядит готовой записью; при `media_retention_days` звук через N дней удаляется —
  остаётся только обрывок текста. Потеря данных по цепочке.
- **Исправление:** запоминать прежний статус в элементе очереди и возвращать его в `finally`; в
  `api_meeting_cut`/`api_video_subtitles` требовать `status == "completed"` (как уже делают перевод и дубляж).

### В3. Живые субтитры при отказе воркера: буфер звука растёт без предела, процесс перезапускается каждые 1,2 с [З]
- **Где:** `app/live.py:192` (`self.audio = np.concatenate(...)`), `:200-211` (`step` ловит исключение, буфер
  не обрезается), `:254-262` (обрезка только после успешного `transcribe`), `:81-104` (`_CaptionWorker.transcribe`:
  при ошибке `_kill()` и до двух `_start()` на каждый вызов).
- **Сценарий:** запись с субтитрами, модель не грузится (не скачана, мало VRAM, сломан CUDA). Каждый кусок
  звука → падение → буфер растёт, воркер поднимается заново. Проверено: за 10 минут буфер 600 с / 38 МБ и 329
  перезапусков; за 3 часа ≈ 690 МБ и тысячи spawn процессов с загрузкой Whisper (и попыткой скачать модель).
- **Исправление:** при исключении обрезать буфер до `LIVE_WINDOW_SEC`; после N неудачных стартов — пауза
  30–60 с и понятная ошибка в `state()`; буфер хранить списком чанков. Также `readline()` воркера без
  таймаута (`live.py:91`) — при зависании CUDA поток пула блокируется навсегда, субтитры «замирают» молча [П].

### В4. Архив обновления может писать файлы вне папки программы [З]
- **Где:** `app/updater.py:341-347` (`rel = n[len(prefix):]`, фильтр только `..` и PROTECTED по первому
  сегменту), `:357` (`dest = app_dir / rel` — абсолютный `rel` даёт абсолютный путь); то же в откате
  (`extractall`).
- **Сценарий:** запись `VerbaScribe-v9/C:/Users/x/.../Startup/x.bat`: `rel.split("/")[0]` = `C:` не в PROTECTED,
  `..` нет, `Path(app_dir) / "C:/..."` = `C:/...`. Проверено: файл записан вне `app_dir`.
- **Последствия:** защита в глубину: архив проверен по хешу, но хеш берётся из того же релиза (В5). Релиз с
  подменённого аккаунта пишет куда угодно (хотя и так заменяет код программы).
- **Исправление:** отбрасывать `Path(rel).is_absolute()`, `rel` с `:`/`\\`/ведущим `/`; перед записью
  проверять `(app_dir / rel).resolve().is_relative_to(app_dir.resolve())`.

### В5. Контрольная сумма обновления не независима от релиза; автообновление ставится без клика и поверх git-клона [Ч]

- **Сценарий:** (а) компрометация аккаунта/токена CI → zip и SHA256SUMS.txt заменяются вместе, проверка проходит,
  код исполняется у всех с `update_auto=true` (по умолчанию) при закрытии окна, без клика. (б) Запуск из git-клона с

- **Исправление:** подписывать SHA256SUMS.txt (minisign/ed25519, ключ в коде, шаг в release.yml), проверять
  подпись в `_download`; `can_install = ... and not git_checkout`; автоустановку на выходе — только после явного
  согласия пользователя в настройках (или оставить только скачивание, установка — по кнопке); Actions закрепить по SHA,
  релиз публиковать через встроенный `gh release create`.

- **Где:** `app/api/system.py:103-114` (отбрасывается только префикс `llm_key_`), `app/database.py:339-350`

  через диалог; согласие проверять в `_cloud_target()`; в `api_record_finish` создавать запись в базе **до**
  удаления частей.

### В7. Нет проверки Origin: страница с другого порта 127.0.0.1 ходит в API с cookie [З]
- **Где:** `app/main.py:207-231` (middleware: только Host и cookie), `:81-84` (имя cookie с портом не
  изолирует её — браузер шлёт cookie на все порты хоста).
- **Сценарий:** cookie `SameSite=Strict` отрезает чужие сайты (проверено: без cookie все 162 маршрута → 401,
  Host-подмена → 403). Но для SameSite «site» не включает порт: страница `http://127.0.0.1:<другой порт>`
  (любая локальная веб-программа, dev-сервер, Jupyter) делает `fetch('http://127.0.0.1:<порт VerbaScribe>/api/...',
